`getCombinedFatherRepayments()` (`expense-app-v37-demo.html` ~line 5895, helpers `normalizeRepaymentKey` ~5883, `getFatherRows` ~5886, `getFatherNetAmount` ~5891, `getTotalFatherRepayments` ~5920) merges manual `fatherHistory` entries with expense rows tagged "חוב לאבא", de-duplicating purely on `` `${toIsoDate(date_raw)}__${amount.toFixed(2)}` ``. No row identity is used. If a genuinely separate second repayment shares date+amount with a history entry, the expense-row copy is silently dropped from every father-debt display (dashboard widget, yearly summary, debt-details modal all read only `getCombinedFatherRepayments`/`getTotalFatherRepayments` — none fall back to the raw expense row). Documented as **C-4** in `00_PROJECT_CONTROL/CALC_LOGIC_MAP.md` §5.

**Confirmed NOT to touch the main balance/forecast:** `getDisplayedClosingBalance` (~5479) and `buildForecast` only subtract bank loan principal (`getLoanScheduleEntryForSheet`), never father repayments. `getExpenseStats` (~5452) sums every row unconditionally regardless of father-tag. So blast radius is confined to the father-debt tracker's own "paid so far / remaining" figures — this is why C-4 is lower urgency than [[project_forecast_double_count_c3]] even though both are real.

**Empirical finding (2026-09-13, checked the real backup, not just the demo):** `backups/raz-expenses-backup-2026-09-13_01-08.json` already contains the exact collision pattern live. `fatherHistory` has `{date_raw:"23/03/2026", amount:1000, description:"העברה בנקאית"}` (this is the hardcoded seed `FATHER_REPAYMENTS_HISTORY` verbatim — no manually-added "ידני" rows exist in real data yet). The entire backup has exactly one expense row anywhere tagged "חוב לאבא" (grepped, count=1): sheet row 43, `{date_raw:"23/03/2026", amount:1000, merchant:"חוב לאבא על מוסך לאוטו - ציריות", category:"רכב/דלק"}`. Same date, same amount as the history entry → currently merged/hidden by the existing dedup. Content is plausibly the *same* real transfer logged twice for two different views (generic bank-transfer note in history vs. specific merchant note in the expense ledger) — but this cannot be confirmed from data alone.

**Open question that must be resolved before implementing anything (and before writing the before/after numeric example CLAUDE.md requires for calc changes):** ask Raz directly — was the 23/03/2026 ₪1,000 "מוסך לאוטו" payment to his father the same transfer as the generic "העברה בנקאית" history line, or two separate ₪1,000 payments? If separate, the debt modal's "שולם עד כה"/"יתרה" figures are *already* wrong by ₪1,000 today, not just a theoretical edge case — that would upgrade this from "reviewed risk" to "confirmed live bug," matching how C-3 got escalated.

**Fix directions evaluated:**
- Widen the key with merchant/notes text — rejected. The one real colliding pair shares zero overlapping text ("העברה בנקאית" vs "חוב לאבא על מוסך לאוטו"), so this would break the correct-merge case it's supposed to preserve without reliably preventing new collisions.
- Explicit manual link field (history row ↔ specific expense row) — most architecturally correct, but expense rows have no stable cross-sheet id today (only `row`, a per-sheet sequence number assigned in `addNewExpense` ~line 7682, reset per sheet) — would need that plumbing first, plus new picker UI. Disproportionate to current frequency (one occurrence across ~1.5 years of data).
- Recommended: **keep today's auto-merge behavior (don't touch the sums — the one known real pair is likely a correct merge and must not regress into double-counting), but stop it being silent.** Add a visible marker on the merged history row (e.g. "מוזג עם הוצאה מ-23/03/2026, ₪1,000, גיליון X") so Raz/Shira can catch a wrongly-auto-merged pair and fix it manually via the existing `addFatherHistoryRow`/`deleteFatherHistoryRow` tools. Cheap anchor point already exists: the per-row list template at ~line 8376 already renders `row.source` — extending it with a merge-badge is a small, low-risk change, not a new UI paradigm. Explicitly do **not** implement "always show both and sum both" — that flips the one known real pair from correct-today to double-counted-from-day-one.

**Adjacent finding, not C-4 itself (found while tracing the same functions, worth a separate CALC_LOGIC_MAP.md line next time, candidate "C-6"):** `renderDashboardHero` (~line 6195-6198) shows `monthlyExpenses = getExpenseStats(selectedSheet).total` (includes every father-tagged expense row unfiltered) side by side with `monthlyDebt` which adds `getFatherRepaymentTotal(selectedSheet)` on top — so a father repayment logged as an expense row appears in both the "הוצאות" card and the "חוב" card on the same screen. Does not corrupt `getDisplayedClosingBalance` (confirmed separate code path, doesn't reference father totals), so it's a display/UX-correctness issue, not a balance-corruption one. Low urgency, not blocking C-4.

**Status 2026-09-13, updated same day:** Raz confirmed directly (asked via AskUserQuestion) — the 23/03/2026 collision is the same transfer logged twice, not two separate payments. Not yet promoted to production — still needs the live behavioral check against this exact real case (does the badge render correctly for the 23/03/2026 pair, do totals stay unchanged) before it goes out, same discipline as C-3.
