`buildForecast()` (`expense-app-v37-demo.html` ~line 6081, byte-identical in production `expense-app-v37.html` — verified, not assumed). `closing` (from `getDisplayedClosingBalance`) already subtracts ALL rows in the sheet, including rows dated later this month but already known (mainly credit-card cycle imports with a future billing date). `avgDaily` was computed from that same `stats.total` (all rows, past+future) ÷ days elapsed, then `projectedSpendRest = avgDaily × remainingDays` is subtracted again from `closing` — a known future charge gets counted twice. Documented as **C-3** in `00_PROJECT_CONTROL/CALC_LOGIC_MAP.md`.

**Confirmed 2026-09-13** via Raz's live reproduction on the demo (not just code reading — this is the right process, matches the doc's own "לא לתקן לפני שיש מספרים" rule): opening 10,000, past expense 4,000 (day 5), future expense 6,000 (day 28), today = day 13/30 → tile showed projected = -13,894 instead of a much smaller real deficit. Same code exists verbatim in production, so real forecast numbers shown to Raz/Shira today are already affected whenever a sheet has future-dated known charges (routine here, given how credit imports work).

**Proposed fix reviewed and approved with required changes:** compute `avgDaily` from only rows with `date_raw` ≤ today (`pastSpend`), not from `stats.total`. Directionally correct, independently re-verified with the same numbers (-6,048 post-fix). Required before implementing:
1. Use the existing `getTodayIso()` helper (already used identically at ~5533, ~5583, ~5588 for "has this already happened" checks) for the "today" cutoff instead of a hand-rolled UTC conversion — `toISOString()`-based "today" drifts a calendar day off from `today.getDate()` during early morning hours in Israel local time.
2. Update the stale comment directly above `buildForecast()` (currently claims it only reads `getDisplayedClosingBalance` + `getExpenseStats`).
3. **New follow-up, not blocking this patch but must be checked before promoting to v37 (candidate C-5):** the `"forecast"` line-chart renderer (~line 6620-6683, `renderChart`/chart type `"forecast"`) computes its own independent "actual today" baseline (`lastActual`, from per-day-dated rows only — never included future rows or the loan-principal deduction, so it never had the C-3 bug). Pre-fix, the chart and the tile already disagree in magnitude on the same sheet (verified: -7,077 vs -13,894 in the test case). **Post-fix they disagree in sign** (chart ≈ +769 surplus vs tile ≈ -6,048 deficit) — worked out from the same test numbers. Recommend logging this as a new tracked item in `CALC_LOGIC_MAP.md` and visually checking the "forecast" chart view on the same seeded test case before promoting, rather than silently shipping a starker on-screen contradiction between the two forecast widgets.
4. Rows with a blank/unparseable `date_raw` (reachable: `addNewExpense` ~line 7640 allows an empty date field) are silently excluded from `pastSpend` — safe direction (still fully counted once in `closing`) but should be a documented decision, not incidental behavior.
