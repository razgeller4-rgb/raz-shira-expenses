`LOAN_SCHEDULE` (`expense-app-v37-demo.html` line 2724, byte-identical in production) is a real 36-installment amortization table, each row `{installment, dueDate, total, interest, principal}` with `total = interest + principal` holding exactly on every row (verified by summing all 36: Σinterest = 4,206.43, Σprincipal = 30,000.00 exactly, Σtotal = 34,206.43 — the round 30,000 principal base is a strong internal-consistency check). `.interest` is read nowhere in the app except the array literal itself — confirmed by grep, zero other matches. Every consumer reads `.principal` only, so every "how much loan payment this month" display understates reality by that month's interest (₪6.65–₪255.00 depending on installment).

**Classification (Raz's A/B split) confirmed correct in spirit:** Group A ("cash that actually leaves this month" — should become `.total`) vs Group B ("how much of the original loan principal is still outstanding" — correctly stays `.principal`, since interest never reduces principal owed). All of Group B (`bankPaidPrincipal`/`bankRemaining`/`bankProgress` ~8295-8302, `getLoanPrincipalBase()` ~2837, `totalDebtRemaining` in `getDashboardWidgetCatalog` ~5535-5537, `bankRemaining` in `getYearlySummaryData` ~5590-5592) is correctly principal-only and explicitly labeled "קרן" in the UI — leave untouched.

**One Group-A location missing from the 6 Raz listed:** `getYearlyRowsData` (~5559-5582) computes `loanEntry` once and reads `.principal` from it **twice** — once at line 5566 for `monthlyBalance`/`runningBalance` (the one Raz found), and again at line 5578 in the returned field `loan: loanEntry?.principal || null`. That second field feeds the yearly table's own "הלוואה חודשית" column (`getYearlyColumnCatalog` id `"loan"`, line 5658 — on by default per the `yearlyColumns` list at line 2707). If only line 5566 is fixed and 5578 is missed, the yearly table would show a `monthlyBalance` column that already reflects interest sitting next to a `loan` column that still doesn't — self-contradicting math in the same row, worse-looking than today's uniform understatement. **Must fix both together.**

**Independent bug found during verification, NOT part of C-2, do not bundle into the same commit (candidate C-7):** `getTotalDebtRemainingSummary()` (line 2830-2836, byte-identical in production, only caller is `renderDashboardHero`'s `debtChip` at line 6219) computes `bankPaidPrincipal` by summing `.principal` over the **entire unfiltered** 36-row schedule — which by construction is always exactly equal to `getLoanPrincipalBase()`. So `bankRemaining = base − base = 0`, **always**, regardless of today's date; not a drift-over-time bug, structurally broken since day one. This is a different root cause than C-2 (no date filter, unrelated to interest/principal/total) but same file/domain, found while tracing the same functions — same pattern as how C-5/C-6 were spun out of C-3/C-4 reviews. Three sibling implementations of the same "bank principal remaining" calc (~5535-5537, ~5590-5592, ~8295-8298) all correctly filter by `toIsoDate(entry.dueDate) <= todayIso` — only this one doesn't.
**Real impact, computed from the live backup (`backups/raz-expenses-backup-2026-09-13_01-08.json`, debt tracking `enabled:true` for Raz, `fatherDebtStart:25000`):** the dashboard hero chip "יתרת חוב כוללת (בנק + אבא)" currently shows **₪16,500** (father-only; bank always reads as 0) instead of the correct **₪34,941.50** (₪18,441.50 bank remaining as of 2026-09-13 [installments 1-15 due] + ₪16,500 father) — understating the headline combined-debt number by **₪18,441.50**. If father debt is ever fully repaid, this chip would disappear entirely (`debtSummary.total > 0` check) even with ~₪18K+ still owed to the bank. Meanwhile the debt tab's own hero figures (`debtBankRemainingHero`, lines 8306/8298) already show the correct filtered number — so today there are already two different "how much bank debt is left" numbers on two screens of the same app, disagreeing by the full principal base. Recommend logging as a new line in `00_PROJECT_CONTROL/CALC_LOGIC_MAP.md` (next id after C-6, i.e. C-7) and fixing separately after C-2 ships, with its own before/after numbers — don't fix opportunistically inside the C-2 commit (violates the project's "one change at a time" rule and would muddy C-2's before/after verification).

**Pre-existing, separately-tracked gap that the proposed fix does not close (already documented in `CALC_LOGIC_MAP.md` §3/§6 as "יורש את C-2"):** the "forecast" line chart (`renderChart`, `type==="forecast"`, ~6649-6697) computes `actual`/`projData` purely from `opening + income − dated expenses`, and never references the loan schedule at all — confirmed by code reading (no `.principal`/`.interest`/`getLoanSchedule` in that block). The hero tile's forecast (`buildForecast` → `getDisplayedClosingBalance`) already deducts principal today and will deduct principal+interest once C-2 ships; the chart deducts neither, unchanged. Pre-fix the tile-vs-chart gap on the same screen was already ~₪818 (principal only, per the C-3 fix note); post-fix it grows to roughly principal+interest for that month (~₪950-1070 depending on installment) — same "two widgets disagree on the same number" pattern as C-5. Not a reason to block C-2, but should be an explicit, acknowledged decision (fix the chart in the same pass, or re-file the remaining gap under its own id) rather than silently marking C-2 "closed" while this half remains open.

**Regression risk the fix introduces, worth a guard before shipping:** `updateLoanScheduleRow(installment, field, value)` (line 4977-4982) does a blind `{...row, [field]: value}` overwrite; the only editable fields exposed in the UI (`renderLoanScheduleRows`, ~8226-8235) are `dueDate` and `principal` — there is no input for `interest` or `total` anywhere in the app. Today that's harmless (everything reads `.principal`, so editing the one editable field keeps every display consistent). After C-2 ships, `.total` becomes the field driving every cash-flow display, but it stays non-editable and is never recalculated when `principal` is edited — so any future manual correction to a row's principal (e.g., bank restructure) will silently desync `.total`/`.interest` from the edited `.principal`, with zero UI indication and no field to fix it through. Recommend either auto-recomputing `total = principal + interest` (keeping that row's `interest` fixed) inside `updateLoanScheduleRow` when `field==="principal"`, or at least surfacing `interest`/`total` as visible (even if read-only) so drift is caught, before relying on `.total` as the primary displayed figure long-term.
