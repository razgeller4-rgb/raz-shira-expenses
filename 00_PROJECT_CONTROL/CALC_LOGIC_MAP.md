## 1. יתרת פתיחה — `getDisplayedOpeningBalance(sheet)` · שורה 5203

```js
if (manual.openingBalance != null) return manual.openingBalance;   // עדיפות 1
if (currentUser === "raz") {                                        // עדיפות 2
  const summary = getSheetSummaryByName(sheet);
  if (summary.opening != null) return summary.opening;
}
return null;                                                        // אחרת
```

### 🔴 C-1 — אסימטריה בין רז לשירה

הנפילה־אחורה ל-`getSheetSummaryByName` **מותנית ב-`currentUser === "raz"`**. לשירה אין מסלול שני.

**התוצאה בשרשרת:** אם שירה לא הגדירה `openingBalance` ידנית →
`opening = null` → `getDisplayedClosingBalance` מחזיר `null` → `buildForecast` מחזיר `{closing:null}` → **גם היתרה וגם התחזית מוצגות כ-`—`**.

**לאמת:** להיכנס כשירה ולבדוק אם הדשבורד מציג יתרה. אם לא — זו כנראה הסיבה, ולא באג תצוגה.

## 3. תחזית סוף חודש — `buildForecast()` · שורה 6081 (עודכן 2026-09-13)

```js
avgDaily            = stats.total / dayNow;
remainingDays       = daysInMonth − dayNow;
projectedSpendRest  = avgDaily × remainingDays;
projected           = closing − projectedSpendRest;
```

מוצג למשתמש (שורה 5940): *"בקצב ההוצאות הנוכחי (X/יום), צפוי להישאר Y בסוף החודש"*.

### 🔴 C-3 — חשד לספירה כפולה

`closing` כבר גורע את **כל** ההוצאות הרשומות בגיליון — כולל כאלה שמתוארכות להמשך החודש (חיובי אשראי עתידיים במחזור, הוצאות קבועות).

`avgDaily` מחלק את **אותו** `stats.total` במספר הימים שחלפו, ואז מכפיל בימים שנותרו — **ומחסיר שוב** מ-`closing`.

**התרחיש הבעייתי:** היום ה-10 בחודש. נרשמו 10,000 ₪ הוצאות, מהן 6,000 ₪ מתוארכות ל-28 בחודש.
- `closing` כבר הפחית את כל ה-10,000
- `avgDaily = 10,000/10 = 1,000`
- `projectedSpendRest = 1,000 × 20 = 20,000`
- `projected = closing − 20,000` — **הפחתה של 20,000 נוספים על הוצאות שכבר נספרו**

**למה זה סביר דווקא כאן:** האפליקציה מייבאת חיובי אשראי למחזור שלם מראש, כולל תאריכי חיוב עתידיים. כלומר `stats.total` כמעט אף פעם אינו "מה שהוצאתי עד היום".

### ✅ תוקן 2026-09-13 — אומת עם מספרים אמיתיים לפני ואחרי

**תהליך:** אימות אמפירי חי על הדמו (לא רק קריאת קוד) → סקירת `domain-risk-reviewer` לפי דרישת CLAUDE.md → יישום → אימות חוזר חי.

**תרחיש הבדיקה בפועל:** גיליון "ספטמבר 26" (החודש הנוכחי, 13/30 ימים), `opening=10,000`, הוצאה 4,000 ב-05/09 (עבר), הוצאה 6,000 ב-28/09 (עתיד ידוע), ניכוי קרן הלוואה 817.57.

| | לפני | אחרי |
|---|---|---|
| `avgDaily` | 769.23 (כולל את ה-6,000 העתידיים) | 307.69 (רק הוצאות עם `date <= היום`) |
| `projected` | **-13,894.49** | **-6,048.34** |

**התיקון:** `avgDaily` מחושב עכשיו מ-`pastSpend` (סכום שורות עם `toIsoDate(date_raw) <= getTodayIso()`) במקום מ-`stats.total` (הכל, כולל עתיד). `getTodayIso()` היא פונקציה קיימת שכבר משמשת לאותו pattern בדיוק בחישובי חוב לבנק/לאבא (עקביות + נמנע מבעיית timezone של `toISOString()`). `closing` ממשיך לשקף את כל מה שידוע (כולל חיובים עתידיים) ללא שינוי; `avgDaily`/`projectedSpendRest` הפכו להעריך רק הוצאה **נוספת, לא-מתוכננת**, מעבר למה ש-`closing` כבר יודע.

**ממצא נלווה שהתגלה בסקירה (C-5):** גרף התחזית (`renderChart`, `type==="forecast"`) מחשב את קו ה"בפועל" וההיטל שלו בנתיב עצמאי לגמרי (`expByDay`), בלי לעבור דרך `buildForecast`/`getDisplayedClosingBalance` ובלי לנכות את קרן ההלוואה. באותו תרחיש בדיוק, לפני התיקון השני: הכרטיסייה -6,048 מול הגרף **+769** בסוף החודש — **סימן הפוך על אותו מסך**. תוקן: קו ההיטל בגרף מטמיע עכשיו הוצאות עתידיות ידועות ביום האמיתי שלהן (`runFutureExp`), בנוסף למגמת `avgDaily`. אחרי התיקון: הגרף מסיים ב-**-5,230.77** — אותו סימן כמו הכרטיסייה. הפער הנותר (~818 ₪) הוא שהגרף עדיין לא מנכה את קרן ההלוואה — פער קטן יותר, נפרד, לא תוקן כאן (יורש את C-2).

**קבצים:** תוקן ב-demo, אומת חי, קודם ל-production באותו סבב (שני התיקונים ביחד — לא לקדם את תיקון הכרטיסייה בלי תיקון הגרף, כדי לא ליצור סתירה חדשה וברורה יותר בין השניים).

## 4. מאזן זוגי — `getSharedExpenseSummary()` · שורה 4510

```js
// שלב 1 — מהוצאות משותפות
entry.payerId === currentUser  →  netBalance += entry.partnerAmount   // הפרטנר חייב לי
entry.payerId === partnerId    →  netBalance −= entry.partnerAmount   // אני חייב לפרטנר

// שלב 2 — סליקות
s.paidById === partnerId && s.receivedById === currentUser  →  netBalance −= s.amount
s.paidById === currentUser && s.receivedById === partnerId  →  netBalance += s.amount
```

**פרשנות:** `netBalance > 0` → הפרטנר חייב לי. `< 0` → אני חייב.
**חשוב:** התוצאה **תלוית-משתמש** (`currentUser`). רז ושירה אמורים לראות מספרים הפוכים בסימן. אם שניהם רואים אותו סימן — זה באג.

**מוחזר גם:** `totalShared` (כל התקופות), `monthShared` + `monthCount` (החודש הנבחר בלבד).

## 5. חוב לאבא — שורות 5624–5636

```js
getFatherNetAmount(row) = row.direction === "increase" ? −amount : +amount
```
`repayment` מקטין את היתרה · `increase` (הלוואה נוספת) מגדיל.

**איחוד מקורות** — `getCombinedFatherRepayments()`: היסטוריה ידנית + שורות הוצאה מכל הגיליונות, עם dedup לפי `normalizeRepaymentKey(date_raw, amount)`.

### ✅ C-4 — תוקן חלקית 2026-09-13 (שקיפות, לא שינוי סכום)

המפתח (`date+amount`) אינו כולל מזהה ייחודי. **שני החזרים אמיתיים באותו יום ובאותו סכום ייחשבו לאותו החזר**, ואחד מהם נעלם בשקט מהחישוב.

**אומת מול production בפועל:** `domain-risk-reviewer` בדק את גיבוי ה-production העדכני ומצא את ההתנגשות הזאת חיה כבר היום: 23/03/2026, רשומת היסטוריה "העברה בנקאית" 1,000 ₪ מול שורת הוצאה "חוב לאבא על מוסך לאוטו" 1,000 ₪, אותו תאריך ואותו סכום.

**נשאל רז ישירות (2026-09-13):** האם זו אותה העברה או שני תשלומים נפרדים. **תשובה: אותה העברה** — המיזוג נכון, לא אבד כסף. בניגוד ל-C-3/C-5, כאן לא היה מספר שגוי בפועל.

**התיקון שיושם:** לא לשנות שום סכום (המיזוג הקיים אומת כנכון למקרה האמיתי היחיד שקיים) — אלא להפסיק להסתיר אותו. `getCombinedFatherRepayments()` רושם עכשיו על כל רשומת היסטוריה אילו שורות הוצאה מוזגו לתוכה (`mergedWith`), ותג "🔗 מוזג עם: ..." מוצג לצד הרשומה. אם מיזוג עתידי יהיה שגוי (שני תשלומים אמיתיים שונים), אפשר יהיה **לראות** אותו ולתקן ידנית (למחוק את רשומת ההיסטוריה השגויה) — במקום שהוא ייעלם בלי עקבות.

**מה עדיין פתוח:** מזהה קבוע לשורת הוצאה (חוצה-גיליונות) לא קיים היום — קישור מפורש (רשומת היסטוריה ↔ שורת הוצאה ספציפית) ידרוש תשתית נוספת. נדחה עד שהתבנית תחזור על עצמה בפועל.

**ממצא נלווה שהתגלה תוך כדי (מועמד C-6, לא תוקן):** `renderDashboardHero` מציג `monthlyExpenses` (כולל שורות "חוב לאבא") **וגם** `monthlyDebt` (שמוסיף את אותן שורות שוב) זה לצד זה על אותו מסך — כפילות תצוגה, לא שחיתות מאזן (לא נוגע ב-`getDisplayedClosingBalance`). לתעד בסבב הבא שנוגעים כאן.
